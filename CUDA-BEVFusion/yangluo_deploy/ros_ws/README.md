# ARM64 ROS1 build and bag smoke test

The node does not use `cv_bridge`; JPEG decoding is provided by the existing
adapter.  The core's undistortion code is explicitly linked to OpenCV 4.5 in
`/ota/miniconda3/envs/ros`.  Do not let CMake select the system OpenCV 4.8.

Mount or copy both `CUDA-BEVFusion` and its sibling `libraries` directory into
the ARM64 container.  The checked local dependency
`libraries/3DSparseConvolution/libspconv/lib/aarch64_cuda13.0/libspconv.so`
is a real AArch64 ELF (not an LFS pointer) and contains Blackwell/SM110 support.
The build therefore defaults to CUDA 13.0 and SM110.  Both remain overridable
if the vehicle SDK later changes.  Then run:

```bash
cd /workspace/CUDA-BEVFusion
# Optional only when the directories are not siblings:
# export YANGLUO_SPCONV_ROOT=/path/to/libspconv
# Optional only if the target reports a different architecture:
# export YANGLUO_CUDA_ARCHS=110
bash yangluo_deploy/tools/check_arm64_environment.sh
bash yangluo_deploy/tools/build_arm64.sh
```

The script defaults to four parallel build jobs under QEMU.  Override with
`YANGLUO_BUILD_JOBS` only after checking host RAM.  CUDA 13's CCCL headers
require actual C++17 syntax.  The isolated `nvcc_cxx17_wrapper.sh` replaces
only NVCC's upstream `-std=c++14` argument with `-std=c++17`; host C++ and the
passenger-car CMake path remain unchanged.

The checked-in ONNX protobuf C++ files were generated by protoc 3.21.12, while
the ROS SDK consistently supplies protoc, headers and `libprotobuf` 3.15.8.
The build script copies only required sources to
`yangluo_deploy/generated/core_source`, regenerates protobuf there with 3.15.8,
and builds in `yangluo_deploy/generated/build_arm64_core`.  It never overwrites
the original `src/onnx/*.pb.*` files.

The current QEMU container has no GPU, so use decode-only mode there.  It
proves ROS deserialization, JPEG decode, PointCloud2 field conversion and
three-stream synchronization, but performs no CUDA inference:

```bash
source yangluo_deploy/ros_ws/devel/setup.bash
bash yangluo_deploy/tools/prepare_decode_only_runtime.sh
export LD_LIBRARY_PATH=/tmp/yangluo_cuda_driver_stub:$LD_LIBRARY_PATH
roscore &
roslaunch yangluo_bevfusion yangluo_decode_only.launch \
  config:=/workspace/CUDA-BEVFusion/yangluo_deploy/configs/runtime.yaml \
  classes:=/workspace/CUDA-BEVFusion/yangluo_deploy/configs/classes.txt
```

`yangluo_bevfusion_decode_only_node` is deliberately GPU-free: it compiles
the same config, JPEG codec, PointCloud2 conversion and frame synchronizer
sources directly, but does not link TensorRT, CUDA, spconv or the inference
core.  This avoids treating QEMU/no-GPU loader behaviour as a vehicle-runtime
test.  The production `yangluo_bevfusion_node` remains unchanged for Thor.

The temporary `libcuda.so.1` link points to NVIDIA's official CUDA link stub.
It avoids loading the incomplete vehicle `libcuda.so.1` in the QEMU container,
whose real `libnvrm_gpu.so` and `libnvrm_mem.so` dependencies exist only on the
vehicle.  Do not use this stub path on real Thor.

In another shell, play only the required topics:

```bash
rosbag play /workspace/CUDA-BEVFusion/yangluogang/yangluo_truck_701_2026-09-17-13-17-04_27.bag \
  --topics /df/camera/0/image/compressed /df/camera/5/image/compressed \
           /perception/lidar/concated_points_cloud
```

Success is repeated `decode_only synced_frames=N` with increasing `N` and no
decode/layout exception.  On real Thor, generate and load-test all FP16 plans,
then set `decode_only:=false`.  Validate the output without altering the bag:

```bash
rostopic type /perception/bevfusion/objects
rostopic echo -n 1 /perception/bevfusion/objects
rostopic hz /perception/bevfusion/objects
```

Expected type:
`yangluo_bevfusion_msgs/DetectedObjectArray`.  Each object includes class ID
and name, score, 3D position, yaw quaternion, dimensions, planar velocity and
four bottom corners.  `id` is only the index within that frame; it is not a
tracking ID.

When the container runs through x86-to-AArch64 QEMU user-mode emulation,
roscpp communication threads may crash independently of the node logic.  The
GPU-free offline validator exercises the same bag deserialization, JPEG,
PointCloud2 and synchronization sources without a ROS master:

```bash
yangluo_bevfusion_bag_validator \
  --bag /workspace/CUDA-BEVFusion/yangluogang/yangluo_truck_701_2026-09-17-13-17-04_27.bag \
  --config /workspace/CUDA-BEVFusion/yangluo_deploy/configs/runtime.yaml \
  --classes /workspace/CUDA-BEVFusion/yangluo_deploy/configs/classes.txt \
  --duration-sec 30 --max-synced 10
```

Success ends with `OFFLINE_BAG_VALIDATION_OK`.  This is an input-contract
test, not a substitute for production-node and TensorRT-plan testing on Thor.
